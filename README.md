# 湖南大学美食街社交平台

## 项目介绍

湖南大学美食街社交平台是基于大学生创新创业的一个项目，我们研发它的初衷是希望能整理学校周边的美食商铺，为同学们提供服务，方便同学们分享美食。

它是一个 SpringBoot 开发的前后端分离项目，使用了 Redis 集群、Tomcat 集群、MySQL 集群提高服务性能。类似于大众点评，实现了用户登录模块、商户查询缓存、优惠券秒杀、附近的商户推荐、UV 统计、用户签到、好友关注、达人探店等功能。

**技术栈：** SpringBoot + Nginx + MySQL + Lombok + MyBatis-Plus + Hutool + Redis + RabbitMQ

## 一、用户登录模块

### 1.1 工作流程

用户注册/登录时上传手机号和验证码，系统校验手机号与验证码是否一致，以手机号查询用户信息，不存在则新建，最后将用户信息保存到 Redis，并生成随机 UUID 作为 Token。

用户登录后，所有请求经过拦截器校验：携带 Token 访问 Redis，取出对应的 value，判断是否存在，不存在则拦截，存在则保存到 ThreadLocal 中并放行。

### 1.2 Session 转 Redis

一开始使用 Session 实现短信验证，但发现 Session 在多台 Tomcat 服务器中存在共享问题——请求切换到不同服务器时可能找不到对应的 Session，导致数据丢失。改用 Redis 实现登录验证后，因为 Redis 集群中数据共享，完美避免了此问题。

Redis 方案设计时考虑了三个要点：
- 采用合适的数据结构，保证信息存储高效简单
- 采用合适的 Key（UUID），保证唯一、方便且具有有效期
- 采用合适的存储粒度，去除 User 中敏感信息，保证用户信息安全

### 1.3 为什么使用 ThreadLocal

Tomcat 采用线程池处理请求，每个请求对应一个独立线程。在拦截器解析出登录用户后，需要无侵入地把用户信息传递到整个请求链路，同时保证并发安全。

ThreadLocal 将数据绑定到当前线程内部，不同线程数据相互隔离，不存在并发竞争；全链路可直接获取，无需方法传参，代码侵入低，非常适合存储当前登录用户这类线程私有数据。

### 1.4 细节处理

**用户信息脱敏：** 将 User 对象的部分可展示属性封装为 UserDTO（id、名称等），用随机生成的 UUID 作为 Key，保证数据安全。

**双层拦截器：**
- 第一层拦截器对所有请求进行拦截，获取 Token 并从 Redis 中查询用户，存在则刷新 Token 并放行
- 第二层拦截器作用于登录后的用户，刷新 Token 有效期，防止用户被踢出

## 二、商户缓存模块

### 2.1 实现原理

商户信息保存在数据库中（`tb_shop` 商铺表、`tb_shop_type` 商铺类型表）。利用 Redis 缓存实现内存读写来快速查询商铺信息，降低高并发带来的服务器读写压力。

### 2.2 缓存一致性（Cache Aside 策略）

采用**旁路缓存模式（Cache Aside）**，以 DB 为主，缓存为辅：

- **读操作：** 先读缓存，缓存未命中再读 DB，最后将 DB 数据写入缓存
- **写操作：** 先更新 DB，然后直接删除缓存

选择原因：
1. 一致性和稳定性较高
2. 分布式 Redis 中没有提供将数据从缓存写入 DB 的功能
3. 缓存写入远快于数据库写入，出现线程安全问题的可能性更低

**为什么删除缓存而不是更新缓存？**
- 更新缓存：每次更新数据库都需更新缓存，写操作频繁时浪费服务端资源
- 删除缓存：更新数据库时让缓存失效，查询时再更新缓存，更高效

采用**主动更新 + 超时剔除**的综合性方案，给缓存数据加上过期时间兜底，达到最终一致性。

**Canal + 消息队列方案：**「先更新数据库，再删缓存」的策略中，更新数据库成功会产生 Binlog 变更日志。通过 Canal 中间件订阅 Binlog 日志，Canal 模拟 MySQL 从节点接收 Binlog 推送并解析，下游消费端删除 Redis 缓存。MQ 的 ACK 确认机制保证删除成功，失败则重试。该方案直接订阅 Binlog，与业务代码无耦合关系。

> **关键点：** 必须是删除缓存成功后再回 ACK 给消息队列，否则可能造成消息丢失。

### 2.3 缓存穿透

**定义：** 客户端请求的数据在缓存和数据库中都不存在，这些请求直接打到数据库。

**解决方案：布隆过滤器 + 空值缓存 + DCL 分布式锁**

1. 请求到达后先用布隆过滤器快速判断 Key 是否存在
2. 存在则查 Redis 缓存和空值缓存
3. 未命中则获取分布式锁，进行双重判定（DCL）
4. 最后查数据库，数据不存在则添加空值缓存

双重判定锁的意义：避免获取锁的多个请求重复查询数据库。

### 2.4 缓存雪崩

**定义：** 同一时间大量 Key 失效或 Redis 宕机，大量请求打到数据库。

**解决方案：**
- 使用同步锁控制查询数据库的线程，只允许一个线程查库并写入缓存
- 对同一类型信息的 Key 设置不同的过期时间（基础时间 + 随机偏移）

### 2.5 缓存击穿

**定义：** 热点 Key 突然失效，大量并发请求瞬间打到数据库。

**解决方案：逻辑过期 + 互斥锁 + 异步缓存构建**

将过期时间设置在 Value 中，访问数据时从 Value 判断是否过期：
- 未过期：直接返回
- 已过期：获取互斥锁，创建异步线程重建缓存，当前线程返回旧数据

## 三、优惠券秒杀模块

### 3.1 工作流程

用户发起秒杀 → 查询优惠券信息 → 判断秒杀条件（时间、库存）→ 校验一人一单资格 → 扣减库存 → 创建订单 → 返回订单 ID

### 3.2 超卖问题（乐观锁）

**问题：** 多线程并发查询库存时，都判断库存 > 0，导致重复扣减。

**解决方案：** 使用乐观锁，基于库存判断（`WHERE stock > 0`）而非版本号，只要库存 > 0 即可创建订单成功，提高并发成功率。

### 3.3 一人多单问题（悲观锁）

**问题：** 同一用户重复下单，需要保证一人一单。

**解决方案：** 使用 `synchronized` 悲观锁，锁定范围为 userId.intern()（从字符串常量池获取同一引用），保证同一用户串行执行。

> **注意：** 锁必须覆盖整个方法以保证事务提交后锁才释放；必须通过 AOP 代理对象调用方法，否则事务失效。

### 3.4 分布式锁（Redisson）

集群环境下，单体 JVM 锁无效，需要分布式锁。

**SETNX 方案的问题：**
1. **不可重入** — 不支持嵌套调用同一把锁
2. **不可重试** — 只能尝试一次抢锁
3. **超时释放** — 业务执行超时导致锁自动释放
4. **主从一致性** — 主节点宕机后新主节点无锁信息

**Redisson 解决方案：**
- **可重入：** 基于 Hash 结构记录锁名称和重入次数
- **可重试：** 利用 Pub/Sub 发布订阅模式实现线程等待与唤醒
- **超时释放：** 看门狗（Watch Dog）自动续约
- **主从一致性：** MultiLock 连锁方案，所有节点加锁成功才算成功

### 3.5 异步秒杀优化（Lua + RabbitMQ）

**优化前问题：** 秒杀流程串行执行，多步数据库操作导致吞吐量低、响应慢。

**优化方案：**
1. 将优惠券信息存入 Redis
2. 基于 Lua 脚本原子性校验库存和一人一单资格
3. 校验通过后将订单消息发送至 RabbitMQ
4. 立即返回结果给前端（不阻塞等待数据库操作）
5. 消费端（`@RabbitListener`）异步从队列中消费并完成库存扣减和订单入库

**RabbitMQ 核心价值：** 业务解耦、异步处理、流量削峰

### 3.6 消息队列堆积的应对方案

| 层面 | 措施 |
|------|------|
| **线上应急** | 水平扩容消费节点、接口限流、清理超时无效消息 |
| **代码配置** | 调大消费者预取数量、关闭不必要日志、优化 SQL 增加索引、调高队列长度和内存阈值 |
| **架构长期** | 拆分独立队列分散压力、多级队列优先级路由、数据库读写分离与分库分表 |

## 四、其他功能

- **附近商铺推荐：** 使用 Redis GEO 数据结构存储商户地理坐标，支持范围搜索和距离排序
- **UV 统计：** 基于 HyperLogLog 数据结构，内存占用 ≤16KB，误差率 < 0.81%
- **用户签到：** 基于 Redis BitMap 实现，极省内存，支持连续签到天数统计
- **点赞排行榜：** 基于 Redis ZSet 实现，Score 为时间戳，支持按时间排序
- **关注与共同关注：** 基于 Redis Set 集合求交集实现
